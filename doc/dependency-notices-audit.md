# Dependency notice provenance (2026-10-25)

## macOS Voice Lab S6 (2026-10-29)

The official Microsoft `onnxruntime-swift-package-manager` package is pinned to 1.19.2, commit `bbc428e168a0374eb7d0503cdb7c73fdc1d99751`. Its Apple binary archive has SHA-256 `28787ee2f966a2c47eb293322c733c5dc4b5e3327cec321c1fe31a7c698edf68`. Exact MIT texts from both the package and verified archive, plus complete upstream ONNX Runtime 1.19.2 third-party notices, are in root `THIRD_PARTY_NOTICES.md` and therefore About → Licences. No Extensions product or non-CPU execution provider is selected. The Apple runtime is statically linked and uses MLAS, not Intel MKL; the generic all-platform notices do not broaden the Mac dependency allowance. The Mac framework notice gate recognizes this exact component.

Official WeSpeaker ResNet34-LM weights at revision `f0c48c298fd835726c27956a5d617bad7115627e` are CC BY 4.0 per the pinned model card; the toolkit repository is Apache-2.0. The weights remain outside Git and app bundles. Exact file size/hash, attribution and calibration are in `shared/catalog/voice-lab-models.json`. The four LibriSpeech test-clean excerpts are CC BY 4.0, attributed to Vassil Panayotov, with source archive hash, modifications, book/chapter/utterance IDs and the full CC BY legal code recorded in the fixture README and root notices. NumPy and Python ONNX Runtime are throwaway calibration-tool dependencies, never app payloads. English clean-read calibration is not a substitute for the owed Estonian and microphone acceptance checks.

## Windows ML exclusion (2026-10-31)

`Microsoft.WindowsAppSDK` 2.5.1, which CommunityToolkit.WinUI also requires, depends on Windows App SDK ML 2.1.94 → `Microsoft.Windows.AI.MachineLearning` 2.1.74 and on the AI 2.5.5, Search 2.5.5 and Widgets 2.0.5 components. In the self-contained App, Windows ML's ONNX Runtime 1.24.20260504.1 `onnxruntime.dll` won the copy-local conflict against the pinned `Microsoft.ML.OnnxRuntime` 1.19.2 native file (higher file version), and DirectML and the Windows AI/Search/Widgets binaries shipped although VoxClip uses none of them. `VoxClip.App` and its type-check project now reference those five packages at the versions the metapackage resolves with `ExcludeAssets="all"`: they stay in the restore graph, but none of their compile references, build targets, runtime or native files, or WinRT registrations reach the app. Replacing the metapackage with individual components was not viable, because CommunityToolkit.WinUI's dependency would bring the metapackage back (at 1.6.250108002 unless pinned).

An MSBuild item inventory of both RIDs' build and publish lists before and after the change removes only files from those five packages (58 to 63 per list, most of them from the AI component), adds none and changes none, and drops the two `onnxruntime.dll` and `Microsoft.ML.OnnxRuntime.dll` copy-local conflicts. The generated WinRT registration manifest loses only the entries for the removed DLLs. None of the remaining 311 PE and winmd files per RID imports or names a removed component. The App therefore ships the Windows App SDK Base 2.0.4, Foundation 2.3.12, InteractiveExperiences 2.1.9, WinUI 2.3.9, DWrite 2.1.0 and Runtime 2.5.1 files, whose `license.txt` is byte-identical to the metapackage's, and the only `onnxruntime.dll` is the pinned 1.19.2 file, which imports the Visual C++ runtime already required through the vcredist145 Setup prerequisite. The root notices no longer reproduce the Windows App SDK ML and Windows ML Runtime terms and notices, and the first-run agreement covers only the Windows App SDK terms. `apps/windows/build/Assert-OnnxRuntimePin.ps1` fails CI unless each RID's App output carries the pinned RID-native `onnxruntime.dll` and `onnxruntime_providers_shared.dll` byte for byte, the matching managed binding, and no DirectML, Windows AI, Search, Widgets or other ONNX Runtime library.

The root `THIRD_PARTY_NOTICES.md` is the notice payload copied into both apps. This audit records how its Windows dependency sections were selected. The FFmpeg source/runtime notices in the root file are the accepted final R4 texts and were not re-generated here.

## Release decisions and final-file audit

The Windows App SDK 2.5.1 `license.txt` grants redistribution only under Section 3 conditions; the package is not simply MIT-licensed. Its `NOTICE.txt` contains Intel MKL simplified terms, including a restriction on reverse engineering. (The Windows AI MachineLearning 2.1.74 `ThirdPartyNotices.txt` had them too; that package no longer ships.) ADR-030 permits the unmodified official runtime binaries in this pinned package graph as a narrow exception to AGENTS.md rule 4, with their exact terms and notices. It preserves the package terms' open-source and LGPL exceptions and does not change VoxClip's MIT licence. The downstream agreement requirement and final installer payload notice audit remain open under release section 3.7; the policy decision alone does not authorize public redistribution.

The old local full-package inventory showed these exact package paths, but its notice payload predates this audit and cannot verify the current root file.

The pinned source `Cargo.lock` and `src/bins/Cargo.toml` were resolved with `cargo tree --locked --target x86_64-pc-windows-msvc --features windows --edges normal -p velopack_bins` and the corresponding ARM64 target. Each target graph has 224 unique package name/version pairs; only the architecture-specific `windows_*_msvc` crate differs. Removing proc-macro packages and their build-only subtrees leaves 198 package pairs, including Velopack's three workspace crates. This is a conservative dependency graph for the shared `velopack_bins` library and all three binaries, not proof that every listed crate's code is linked into each final PE. Source call paths do establish `zstd` 0.14.0 → `zstd-safe` 8.0.0 → `zstd-sys` 2.1.0+zstd.1.5.7 in Update's patch command. The selected `zstd` default features enable arrays, legacy and dictionary support; `zstd-sys` vendors Zstandard 1.5.7 C source. The source also has Google-copyrighted fastzip files in the shared Rust library, called by Update's patching flow; the source graph alone does not show whether LTO retains them in Setup or the stub. `ureq`'s default Rustls path selects `rustls` 0.23.45, `rustls-webpki` 0.103.15, `ring` 0.17.14 and `webpki-roots` 1.0.9. The selected deflate path includes Rust `zlib-rs` 0.6.8. A missing named file is not evidence that static code is absent.

The root notices now contain exact pinned source/crate texts for the Google fastzip headers, the zstd wrappers/bindings and vendored Zstandard source, ring's ISC/BoringSSL/fiat and once_cell texts, selected ISC and BSD crates, zlib-rs, ICU4X Unicode, and the webpki-roots data agreement. The 24 ICU4X crates in the runtime graph have byte-identical `LICENSE` files; six more with the same licence occur only in the broader graph's build-time proc-macro subtrees. An appendix maps the other 183 selected runtime-graph crate identities to 90 deduplicated exact licence texts from their pinned crates.io archives or the exact VCS commits recorded in `.cargo_vcs_info.json`; its full source hashes are recorded there. The `fs_at` 0.2.1 crate and pinned source commit have no licence file; its pinned manifest declares Apache-2.0 and identifies the author, and the full Apache text is already in the root notices. The Velopack tool package's `vendor/THIRD_PARTY_NOTICES.md` names build tools and is not a distributed Setup/Update/stub inventory.

The release script now hashes all six installed `vpk` vendor inputs before packing; requires each RID's asset metadata to contain one `Full` package, named for the current version and RID; compares that package's `lib/app/THIRD_PARTY_NOTICES.md` with the release root bytes; then compares installed notices, Update and stub with the same RID's full package. This checks pinned input identity and package/install propagation. Because Velopack edits resources and Setup's bundle and Authenticode before release, input hashes cannot be compared directly with final Setup, Squirrel or stub whole-file hashes. These source/package checks do not prove the final linked object inventory; a Windows binary-level comparison remains unverified here. Both apps' About/Settings consumers must display the bundled root notices.
