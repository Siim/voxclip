# Voice Lab v3 upgrade and voice-reference cases

`upgrade-cases.json` holds shared cases for the explicit project upgrade and the own-voice reference transitions (voice-lab.md §6.8, §6.10, §10.1 and §10.5). Both native Core suites replay every case: Mac `VoiceLabUpgradeTests` and Windows `Tracks/voice-lab/VoiceLabUpgradeTests`.

- `projects` maps a name to a complete project document. Every case starts from one of them, and every successful case ends with one.
- `takes` holds the segment and paid-asset records that an `accept` step appends. `own-passage` is the own-voice passage from `passage-render-v3.voxclip`; `stock-changer` is the stock voice-changer segment from `voice-changer-half-render-v3.voxclip`; `legacy-passage` is the version 2 passage from `passage-project.voxclip`, with no scope and no recipes. Each `changer-*` take is `stock-changer` with candidate recipes changed: its selected candidate, its alternative (which some takes reject) or, in `changer-two-candidate-defects`, both.
- Each case has an `id`, an `input` project name and ordered `steps`. A step is `upgradeToV3`, `addVoiceReference` with an inline `voice`, `markVoiceDeleted` with a voice `id`, or `accept` with a `take` name. Each step applies to the previous result. A case with no steps checks that loading `input` refuses with `error`.
- A case ends with `expected`, the name of the resulting project, or `error`, the typed Voice Lab error that the last step throws. Swift compares the `VoiceLabProjectError` case name; C# compares the `VoiceLabProjectErrorCode` name with its first letter lowered.
- The suites compare each platform's saved JSON with the expected project after parsing both and sorting keys, so numbers compare as binary64 values and nulls compare exactly. Every successful result also reloads through Core and, with `VOXCLIP_SCHEMA_PYTHON`, validates against `shared/schemas/project.schema.json`.
- `videoRecipes` maps each render-recipe video mode (`source`, `retimed`, `zoomCover`, `lipsync`) to one `video` object with all 15 keys, `null` where the mode has no value. The Mac suite encodes the same values and must match each object exactly, and the Windows suite must read each one back unchanged. Every key is required, explicit `null` included. Both suites remove keys from the `video` objects of `passage-render-v3`, either all its null keys or any single key, and expect their existing unreadable error, because development builds before 2026-10-26 wrote files without the null keys.

The cases pin these rules. Version 1 and segment-free version 2 projects become version 3 with empty `voices` and `videoAssets` and Clean audio off, keeping assets, transcript, edits, captions, share, export settings and extensions. Any version 2 segment refuses with `legacySegmentsNeedReview`, and version 3 is unchanged. `accept` upgrades first, so it never writes version 2, and accepting the recipe-less `legacy-passage` into version 1 refuses with `missingRenderPolicy` because a version 3 segment must record its scope and recipes. Every stored recipe, rejected or not, must also match the project schema. A rejected alternative with a valid recipe is kept. Each of these refuses with `invalidSegment`:

- on a rejected recipe, an empty chunk list, a missing region, an unsafe quote ID, a negative cost or an empty model;
- on the unselected recipe, a provider outside `[a-z0-9-]+`;
- on the selected stock recipe, a negative transcript token count, a speaker threshold above 1 or an empty speaker model.

Render policy also refuses an unrejected alternative whose endpoint contains `://` with `invalidSegment`, the segment rule's code, because selecting it would copy that endpoint into the segment.

For each candidate in order, an unrejected candidate first passes render policy, then every stored recipe passes the shape check; the first failure is reported, and a shape failure is `invalidSegment`. Two takes with two defects pin that order. A peak at or above 0 dBFS fails only render policy, while a speaker threshold above 1 or an empty speaker model fails only the shape check. With the shape defect on the selected candidate and the policy defect on the alternative, accept refuses with `invalidSegment`. With both defects on the alternative, it refuses with the policy's `qaRejected`.

Voice transitions refuse version 1 and 2 with `requiresVersion3`. A display name has 1–60 Unicode scalars after trimming whitespace, and the trimmed name is stored: 60 Estonian `õäöü` scalars pass, while 61 scalars and 61 decomposed scalars (31 graphemes) refuse with `invalidVoice`. Only an active reference blocks the same provider voice ID. A loaded project with two references that share one ID refuses with `consentUnverified`, the code for every other defect in a single reference. Deleting a voice keeps its reference, segments and assets; deleting it again returns the same project, and a later own-voice accept refuses with `consentUnverified`. That check covers every unrejected own-voice candidate, not only the selected one: a stock-selected take whose unrejected alternative uses a deleted reference refuses, and a rejected own-voice alternative needs no active reference. Upgrading, adding the voice, accepting the own-voice take and deleting the voice reproduces `passage-render-v3.voxclip` exactly.

The inputs come from `interview-take.voxclip`, `passage-project.voxclip`, `passage-render-v3.voxclip` and `voice-changer-half-render-v3.voxclip`. The generator reads those files but never changes them; the voice-lab sources share every field except `schemaVersion` and `voiceLab`. Expected results come from a small independent model in the generator, which also checks that every refusal it makes comes from the last step. The model does not validate, so a case whose result Core validation refuses declares that error; the model must accept every step of such a case. No clock time, randomness, provider output or media is involved.

Regenerate with `python3 tools/fixtures/voice-lab/generate_upgrade.py` from any directory and inspect the diff; two runs produce byte-identical output.
